## 2. 开发顺序与交付物

### M1-01 来源与字段核对

已核实并登记全部 220 个 ERP 模板业务字段，保留原字段名及开发优先级；后续确认其实际数据类型、必填性、唯一性和兼容映射，不再索取这两份模板。
> <sub>All 220 fields have been inventoried. Next verify data types, requiredness, unique keys and import aliases without requesting the same templates again.</sub>

### M1-02 主键、字段权限和关系设计

确认 RFQ Line ID、存货编码及 `往来单位编码`—`供应商编码` 身份关联；同一往来单位可兼具客户、供应商身份；保留 RFQ/报价版本和采购员覆盖属性快照。
> <sub>Validate inventory and RFQ identities, counterparty/supplier role mapping, dual roles and immutable history.</sub>

### M1-03 统一表头与兼容导入

将 M0 演示中的“物料编码／名称／分类”等核心正式字段改为 ERP `存货编码／存货名称／所属类别`；旧粘贴模板仅作为明确标识的别名可识别；导入第 1 行强制为表头，主键必须精确存在。
> <sub>Align M1 labels to ERP canonical names, while supporting explicit legacy aliases. Require exact first-row headers and valid primary key columns.</sub>

### M1-04 结构化实体与迁移

在 M0 功能不回退的前提下建立 RFQ、版本、询价行、往来单位主体、供应商身份、报价历史、档位、证据和审计；联系方式、银行信息及数据协同设置仅预留子表结构。
> <sub>Model RFQs and the canonical counterparty/supplier role while retaining child-table structures without implementing complete child-table interfaces.</sub>

### M1-05 数据保存、恢复和迁移

候选用 IndexedDB + 版本化备份文件，包含导出、导入预览、完整性校验、失败回滚和恢复结果；必须告知跨设备不实时同步。
> <sub>Proposed IndexedDB persistence with schema-versioned backups, validation, rollback and explicit cross-device limitations.</sub>

### M1-06 自动测试及人工验收

沿用 GitHub Actions 和 Playwright，先跑已有 M0 验收，再测试新字段、关系、持久化与恢复。人工验收后用户批准才能合并 `main`。
> <sub>Re-run M0 regression, add M1 tests for names, entities, persistence and restore; merge only after buyer approval.</sub>

## 3. M1 验收标准：字段和导入

同一概念全系统统一 ERP 中文名称；物料、供应商、报价回收、预览、编辑、导出和搜索表头一致；英译仅文档次要显示。
> <sub>Canonical ERP Chinese names should be consistent across item, supplier, quotation, editing, preview, export and search interfaces; English is secondary.</sub>

新模板支持 `存货编码`，`RFQ Line ID` 为另一条身份；旧 `物料编码` 可通过显式兼容规则映射；重复关键值、非唯一匹配必须拒绝自动更新。
> <sub>Use exact inventory-code and RFQ-line keys; map legacy labels explicitly and reject nonunique matches.</sub>

粘贴保留空白列位置，支持 Tab/中英文逗号及引号内分隔符；缺可选尾列允许补空，缺关键列或数量非法必须在预览注明。
> <sub>Preserve blank columns and quoted delimiters in paste input; validate mandatory keys and quantities in previews.</sub>

`采购常用单位`、ERP `主计量`、`计量单位组`、PO `主单位` 与 SRM `询价单位` 未核对前不自动换算，保留原始单位；MOQ 与 MPQ 不合并。
> <sub>Do not convert ERP purchasing/base units, PO units or RFQ units before verification; keep MOQ and MPQ distinct.</sub>

PO 导入只能进入采购订单事实实体，不能自动变为报价；历史谈判 Excel 的“最终价格”必须标明证据等级。
> <sub>PO facts must not become supplier quotations; historical negotiated prices require source evidence.</sub>

## 4. M1 验收标准：模型、历史与比价

- **多对多分配**：不同供应商报价覆盖不一致仍能正常分配、导出和比较。
> <sub>Supplier scopes may vary; keep existing assignments when bulk-selecting, and allow RFQs below full coverage.</sub>

- **版本不可覆盖**：已确认历史不可原位修改；只能通过新版本保留变更。
> <sub>Issued RFQ changes must create new revisions; confirmed quote revisions remain immutable.</sub>

- **阶梯价和报价状态**：未报与报零元严格区分，阶梯价按当前数量档位有效。
> <sub>Keep missing quotes distinct from declined/cannot-supply, and do not fabricate tier or zero prices.</sub>

- **定标与比价**：同范围比较按已确认的采购员选组口径，非最低价保留理由。
> <sub>Comparable totals require buyer-selected groups of two or more suppliers; preserve award reasons and review flags.</sub>

- **凭证链**：报价数据与原始邮件/附件、聊天截图、PDF 来源证据分别记录。
> <sub>Preserve original email/attachment evidence or chat/PDF records, with provenance for manual entries.</sub>

- **真实数据保护**：GitHub 上仅允许匿名测试样本和字段结构。
> <sub>Only synthetic business data may enter GitHub; genuine supplier and purchase records stay private.</sub>

## 5. M1 验收标准：持久化与备份

- **刷新页面后重启程序**：数据及所有关系仍可恢复。
> <sub>Persistence must restore RFQs, assignments, quote history, evidence references and award decisions without duplicates.</sub>

- **备份与恢复**：可校验地完整导出和恢复，不静默覆盖。
> <sub>Use versioned backups with preview and integrity validation for duplicate IDs or broken references.</sub>

- **历史不丢失**：迁移失败不得损坏既有记录。
> <sub>Failed migration or restore leaves the original data intact; schema upgrades require repeatable tests.</sub>

- **跨电脑说明**：本地版本必须明确说明同步限制。
> <sub>Browser-local storage does not sync between devices; document backup and restoration procedures.</sub>

- **附件安全**：证据保存策略单独验收。
> <sub>Evidence files and large PDFs require an approved long-term storage policy.</sub>

## 6. GitHub 开发与测试治理

从已验收 `main` 创建 M1 草稿分支；每一批修改先执行自动逻辑检查、GitHub Actions Playwright 真实 Chromium 流程测试；新增后续字段不得让 M0 的导入、供应商分配、报价历史、同范围比价功能退化。
> <sub>Use dedicated M1 branches based on approved main. Run existing logic and browser acceptance plus new M1 tests before considering merges.</sub>

每次修复按“发现问题 → 原因 → 修复代码 → 回归用例 → GitHub Actions 证据 → 采购员体验”闭环；失败测试不视为已验收。
> <sub>Every defect must have a cause, patch, regression case, CI evidence and buyer UAT; failed checks never qualify as acceptance.</sub>

所有新编写的重要代码注释和正式需求文档使用中文上、英文另行的格式；英文通过 GitHub `> <sub>…</sub>` 显示较淡小字号，不在同一行跟随中文。
> <sub>Keep Chinese-first documentation and comment conventions; English always appears on a separate muted, smaller GitHub quote line.</sub>

**只有用户明确批准后才合并 `main`。本次仅创建文档草稿分支，不执行任何代码变更、数据迁移或合并。**
> <sub>Merging into main requires explicit future approval. This step produces draft documentation only.</sub>

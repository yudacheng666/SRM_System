# 20261009 M1 开发计划、任务分解与验收标准（草案）

> <sub>M1 Implementation Tasks and Acceptance Criteria (Draft)</sub>

**目标：在保留 M0 已验收主分支的前提下，先定字段与模型，再依次开发可保存的真实业务结构。当前为计划草案，尚未授权任何 M1 程序改动。**
> <sub>Goal: lock down canonical fields and schemas before adding persistence and business logic. This plan does not authorize code changes to M0/main.</sub>

## 1. 先决条件与范围

当前 `main` 保存了 M0 人工验收版；新版本一律从主分支创建 `draft/m1-...` 类开发分支。开发中不合并主线、不替换旧 M0；GitHub 仅保存匿名数据与自动测试。
> <sub>Main contains the approved M0 prototype. All M1 changes use isolated draft branches; never merge into main without fresh authorization and never commit actual procurement records.</sub>

ERP 存货主档和供应商主档的完整 Excel 导出表头尚未获取；历史报价表存在多层横向供应商字段。M1 先依据已核实的字段做可扩展架构，不在未确认字段上写死规则。
> <sub>Official ERP master export headers are still missing. Historical quotes have multi-tier grouped headers, so M1 must remain extensible rather than hardcode assumptions.</sub>

## 2. 开发顺序与交付物

### M1-01 来源与字段核对

先交付 `15_数据源字段字典`，逐列标注 ERP 原名、SRM 统一名、历史别名、来源状态、数据类型、可空性；用户提供两个主数据表头后补齐。
> <sub>Deliver a source-verified dictionary with ERP names, SRM labels, legacy aliases, types and evidence levels. Complete it after receiving header-only master exports.</sub>

### M1-02 主键、字段权限和关系设计

确认 RFQ Line ID、存货编码、供应商身份、RFQ/报价版本与历史事实间关系；区分主档自动带出与采购员临时修改，正式发布后锁定快照。
> <sub>Approve identifiers, version relationships and buyer overrides. Issued snapshots and confirmed quote history must be immutable.</sub>

### M1-03 统一表头与兼容导入

将 M0 演示中的“物料编码／名称／分类”等核心正式字段改为 ERP `存货编码／存货名称／所属类别`；旧粘贴模板仅作为明确标识的别名可识别；导入第 1 行强制为表头，主键必须精确存在。
> <sub>Align M1 labels to ERP canonical names, while supporting explicit legacy aliases. Require exact first-row headers and valid primary key columns.</sub>

### M1-04 结构化实体与迁移

在现有 M0 功能不回退的前提下建立分离的 RFQ、RFQ 版本、询价行、供应商分配、报价轮次/版本、报价明细/档位、证据、定标、审计记录。
> <sub>Introduce normalized RFQ, versions, lines, assignments, quote histories, tiers, evidence, awards and audit structures without regressing M0.</sub>

### M1-05 数据保存、恢复和迁移

候选用 IndexedDB + 版本化备份文件，包含导出、导入预览、完整性校验、失败回滚和恢复结果；必须告知跨设备不实时同步。
> <sub>Proposed IndexedDB persistence with schema-versioned backups, validation, rollback and explicit cross-device limitations.</sub>

### M1-06 自动测试及人工验收

沿用 GitHub Actions 和 Playwright，先跑已有 M0 验收，再测试新字段、关系、持久化与恢复。人工验收后用户批准才能合并 `main`。
> <sub>Re-run M0 regression, add M1 tests for names, entities, persistence and restore; merge only after buyer approval.</sub>

## 3. M1 验收标准：字段和导入

同一概念全系统统一 ERP 中文名称；物料、供应商、报价回收、预览、编辑、导出和搜索表头一致；英译仅文档次要显示。
> <sub>同一概念全系统统一 ERP 中文名称；物料、供应商、报价回收、预览、编辑、导出和搜索表头一致；英译仅文档次要显示。</sub>

新模板支持 `存货编码`，`RFQ Line ID` 为另一条身份；旧 `物料编码` 可通过显式兼容规则映射；重复关键值、非唯一匹配必须拒绝自动更新。
> <sub>新模板支持 `存货编码`，`RFQ Line ID` 为另一条身份；旧 `物料编码` 可通过显式兼容规则映射；重复关键值、非唯一匹配必须拒绝自动更新。</sub>

粘贴保留空白列位置，支持 Tab/中英文逗号及引号内分隔符；缺可选尾列允许补空，缺关键列或数量非法必须在预览注明。
> <sub>粘贴保留空白列位置，支持 Tab/中英文逗号及引号内分隔符；缺可选尾列允许补空，缺关键列或数量非法必须在预览注明。</sub>

`采购常用单位`、`计量单位`、PO `主单位` 与 SRM `询价单位` 未核对前不自动换算，必须记录原始单位；MOQ 与 MPQ 不合并。
> <sub>`采购常用单位`、`计量单位`、PO `主单位` 与 SRM `询价单位` 未核对前不自动换算，必须记录原始单位；MOQ 与 MPQ 不合并。</sub>

PO 导入只能进入采购订单事实实体，不能自动变为报价；历史谈判 Excel 的“最终价格”必须标明证据等级。
> <sub>PO 导入只能进入采购订单事实实体，不能自动变为报价；历史谈判 Excel 的“最终价格”必须标明证据等级。</sub>

## 4. M1 验收标准：模型、历史与比价

- **多对多分配**：不同供应商报价覆盖不一致仍能正常分配、导出和比较。
> <sub>不同供应商可报价不同物料，取消/反选/批量关联不得抹除已分配关系；Coverage <100% 允许继续生成询价。</sub>

- **版本不可覆盖**：已确认历史不可原位修改；只能通过新版本保留变更。
> <sub>已发 RFQ 的实质变更形成新 RFQ 版本；已确认的供应商报价及轮次不得原位覆盖，必须支持追溯。</sub>

- **阶梯价和报价状态**：未报与报零元严格区分，阶梯价按当前数量档位有效。
> <sub>真实缺报与显式未报/不供货区分；阶梯数量不匹配时不猜价格，明确报价为 0 与缺价区分。</sub>

- **定标与比价**：同范围比较按已确认的采购员选组口径，非最低价保留理由。
> <sub>采购员选择至少两家供应商后，同范围有效报价金额才能横向比较；非最低价需记录理由，新报价使人工选择待复核时不抹除原记录。</sub>

- **凭证链**：报价数据与原始邮件/附件、聊天截图、PDF 来源证据分别记录。
> <sub>保留供应商邮件及原附件；没有邮件时支持聊天截图、PDF 等原件引用；系统无法识别时仍可手工输入，但来源需说明。</sub>

- **真实数据保护**：GitHub 上仅允许匿名测试样本和字段结构。
> <sub>真实供应商、物料、成交价和证据附件均不得进入 GitHub；全部自动测试只用虚构样本。</sub>

## 5. M1 验收标准：持久化与备份

- **刷新页面后重启程序**：数据及所有关系仍可恢复。
> <sub>已保存的 RFQ、供应商分配、报价版本、附件引用和定标原因能正确恢复，不生成重复记录。</sub>

- **备份与恢复**：可校验地完整导出和恢复，不静默覆盖。
> <sub>可导出带 schema 版本的完整备份；先做恢复校验与预览；损坏、旧结构、重复 Line ID、不存在的供应商引用必须明确拦截或安全迁移。</sub>

- **历史不丢失**：迁移失败不得损坏既有记录。
> <sub>导入或恢复异常时旧数据保持完整；可回滚；升级数据库结构必须有可重复迁移测试。</sub>

- **跨电脑说明**：本地版本必须明确说明同步限制。
> <sub>浏览器本地存储不等于 OneDrive/服务器同步；明确告知当前存储位置、备份机制及换电脑操作步骤。</sub>

- **附件安全**：证据保存策略单独验收。
> <sub>不能假设浏览器存储可永久保存原邮件与大型 PDF；凭证文件长期保管方式需另行决定。</sub>

## 6. GitHub 开发与测试治理

从已验收 `main` 创建 M1 草稿分支；每一批修改先执行自动逻辑检查、GitHub Actions Playwright 真实 Chromium 流程测试；新增后续字段不得让 M0 的导入、供应商分配、报价历史、同范围比价功能退化。
> <sub>Use dedicated M1 branches based on approved main. Run existing logic and browser acceptance plus new M1 tests before considering merges.</sub>

每次修复按“发现问题 → 原因 → 修复代码 → 回归用例 → GitHub Actions 证据 → 采购员体验”闭环；失败测试不视为已验收。
> <sub>Every defect must have a cause, patch, regression case, CI evidence and buyer UAT; failed checks never qualify as acceptance.</sub>

所有新编写的重要代码注释和正式需求文档使用中文上、英文另行的格式；英文通过 GitHub `> <sub>…</sub>` 显示较淡小字号，不在同一行跟随中文。
> <sub>Keep Chinese-first documentation and comment conventions; English always appears on a separate muted, smaller GitHub quote line.</sub>

**只有用户明确批准后才合并 `main`。本次仅创建文档草稿分支，不执行任何代码变更、数据迁移或合并。**
> <sub>Merging into main requires explicit future approval. This step produces draft documentation only.</sub>

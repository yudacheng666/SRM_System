# 20261014 SRM UI V1 Page Audit and Design Proposal (Pending Approval)

## 1. 目标与基线 / Goal and Baseline

- 本阶段目标是让采购员能够顺畅完成询价建立、物料/图纸、供应商分配、报价回收、比价议价及保存备份的完整闭环，并便于 Windows 人工试用。
- The goal is a practical buyer UI for end-to-end RFQ management, items/drawings, assignments, quotes, comparison and safe persistence, suitable for Windows user testing.
- 基线来自已验收并合并 PR #4 的 `draft/20261013-m1-storage-ui-audit`（起始提交 `84a432e44626619bae2d2a168a56d0e623edc1d6`）。
- Baseline: `draft/20261013-m1-storage-ui-audit` after approved PR #4, starting at `84a432e44626619bae2d2a168a56d0e623edc1d6`.
- UI 独立分支为 `draft/20261014-ui-v1`；不得写入或合并 `main`，不得覆盖基线分支。
- The isolated UI branch is `draft/20261014-ui-v1`; do not commit or merge to `main` or overwrite the baseline branch.
- 本文根据当前 HTML 源码和历史审计进行静态结构审查；未宣称对新版布局做过真实浏览器验收。
- This is a static source/architecture review; the proposed layout has not yet undergone real browser acceptance.

## 2. 当前界面的问题 / Current UI Problems

1. 当前顶部工作区同时包含新建、历史切换、手动保存、JSON/ZIP 恢复、导出、供应商导入、图纸管理等大量操作，主要业务区域被推到下方。
1. The top control area mixes creation/history/save, JSON/ZIP restore, exports, supplier intake and drawing management, pushing actual work down the page.
2. 现有五个标签是物料、分配、报价导入、比价、系统设置；缺少清晰的“询价项目列表 → 打开某个询价 → 在该询价中操作”的层级。
2. Five tabs mix four RFQ activities and a global settings page; the project-list-to-project-detail hierarchy is weak.
3. 物料、分配和报价区域同时显示太多按钮、导入途径与高级配置；核心列表与当前操作状态不够突出。
3. Item, allocation and quote screens expose too many controls and advanced choices at once, hiding the table and current workflow state.
4. 存在部分旧文案（例如“候选版”“手动保存”“M0 演示”等），需根据实际功能确认后改成准确提示，不能改文案来掩盖未实现功能。
4. Some labels still refer to pilot/manual-save/M0 demo behavior; replace them only when the actual feature behavior is verified.
5. 图纸批量匹配已具备候选与人工确认，但入口位于全局顶部，应放回“物料与图纸”的操作上下文。
5. Drawing matching has candidate/manual confirmation controls but currently lives in the global toolbar rather than the item context.

## 3. UI V1 信息架构 / Proposed Navigation

```text
SRM / 询价管理                           当前询价 | 自动保存状态 | 用户帮助
├── 询价项目列表（入口）
│   ├── 搜索 / 排序 / 历史 / 新建
│   └── 打开单笔询价 → 询价工作台
│       ├── ① 物料与图纸
│       ├── ② 供应商与分配
│       ├── ③ 报价回收
│       └── ④ 比价议价
└── 管理工具（非业务步骤）
    ├── 数据备份与恢复（S4 与兼容导出区分）
    └── 字段与导入映射（现阶段仅现有字段，不接 ERP）
```

- 主工作台始终显示 RFQ 编号、工作状态、业务数据保存状态及异常提醒；管理工具不可挤占日常业务位置。
- Always show RFQ identity, work status, save status and actionable warnings; keep administrative tools out of the daily flow.
- “供应商管理”在当前询价的“供应商与分配”中；供应商导入和单条添加以独立弹窗/抽屉展开。
- Supplier list, import and single-add live in the current RFQ's supplier/assignment workspace, with modal or drawer intake.
- “原始 PDF 图纸及匹配”在“物料与图纸”中；正式关联仍需确认。
- Original PDFs and filename matching live under Items & Drawings; final associations still require confirmation.

```text
┌─────────────────────────────────────────────────────────────────────┐
│ SRM-Lite     询价项目 / RFQ-xxx          ● 已保存第 N 版   管理工具 │
├─────────────────────────────────────────────────────────────────────┤
│ 项目列表 / 当前询价摘要、物料数量、供应商数量、报价轮次、图纸状态  │
├─────────────────────────────────────────────────────────────────────┤
│ 物料与图纸 | 供应商与分配 | 报价回收 | 比价议价                    │
├─────────────────────────────────────────────────────────────────────┤
│ 页面标题 + 关键指标                     [主要操作] [更多操作]     │
│ [搜索与筛选]                                                      │
│ ┌───────────────────────────────────────────────────────────────┐   │
│ │ 可选择 / 可排序 / 可分页的核心业务表格                        │   │
│ └───────────────────────────────────────────────────────────────┘   │
│ 已选 X 项 → 出现对应批量操作条；导入、编辑、图纸预览用弹窗/侧栏   │
└─────────────────────────────────────────────────────────────────────┘
```

- PC 优先按 1366–1600px 宽度设计；不要求把宽表格强行压窄，可横向滚动、固定表头。
- Optimize first for 1366–1600px desktop screens; wide tables may scroll horizontally with sticky headers.
- 切换业务标签不应修改持久化内容或生成新的 SQLite 修订。
- Switching tabs must not mutate business state or create new SQLite revisions.

## 5. V1 开发次序 / V1 Implementation Order

### UI-1 页面骨架 / Shell

- 先建立统一顶部状态区、项目入口、工作台导航及独立管理入口；保留全部已有功能的可访问性。
- Start with shared header/status, project entry, RFQ navigation and admin entry without deleting access to existing functions.
- 保持现有 DOM 事件 ID、API 路径、快照结构和报价/备份规则不变，优先迁移布局与文案。
- Preserve existing DOM hook IDs, API endpoints, snapshot schema, quotation and backup semantics; move layout and text first.

### UI-2 高频操作 / Daily Workflow

- 物料与图纸：列表优先、导入弹窗/步骤、图纸匹配和人工确认、选择后的批量工具条。
- Items & Drawings: table-first, stepped import, PDF matching/manual confirmation and selection-driven batch actions.
- 供应商与分配：双向分配模式保留，已选物料及当前供应商关联持续可见，追加不覆盖。
- Suppliers & Allocation: preserve both assignment directions; show selected scope and current relationships; append, never overwrite by accident.
- 报价回收：供应商/轮次 → 导入或录入 → 异常校验 → 人工确认；保留多轮和阶梯价。
- Quote Intake: supplier/round → intake → validation → confirmation; preserve rounds and tier prices.
- 比价议价：默认先显示可比结果表、共同范围及最低价提示；分析选项与报告导出放入次级区域。
- Comparison: lead with the actual comparable table, common scope and lowest-price cues; keep advanced analysis/exports secondary.

### UI-3 数据与设置 / Administration

- 数据管理区分类显示 S4 完整恢复 ZIP、JSON 兼容格式、供应商外发 ZIP，使用明确的不可覆盖风险说明。
- Clearly distinguish S4 recoverable ZIP, legacy JSON exports and supplier-facing ZIP in the data-admin view.
- 保留现有字段配置入口和筛选/排序/分页，不在 UI V1 引入真实 ERP 字段或历史采购数据。
- Retain existing field configuration/search/sort/pagination; do not add formal ERP fields or historical procurement imports in UI V1.

## 6. 不得改变的业务约束 / Invariants

- 不影响 SQLite 自动保存、历史修订、多标签 409 冲突检测、首次保存与 24 小时备份策略。
- Do not alter autosave, revision history, 409 conflict handling, initial save or daily backup policy.
- 已确认报价不得静默改写；阶梯价、轮次/版本、同范围比价及非最低价说明仍然可操作。
- Confirmed quotes remain immutable; tiers, rounds/revisions, comparable scope and award reasons remain usable.
- 支持低于 100% 分配覆盖时生成已分配范围的询价单；供应商外发 ZIP 不包含内部 JSON。
- Allow supplier RFQ exports below 100% allocation coverage; external ZIP must omit internal JSON.
- 图纸匹配只建议候选，任何不唯一及不可靠情形必须经人工确认；PDF 原名和字节不变。
- Drawing matches are suggestions only; ambiguous matches require explicit review and original PDF bytes/names remain unchanged.
- 所有 GitHub 文档、代码、示例与截图使用虚构信息；实际业务数据永不进入代码仓库。
- Repository materials must use synthetic information only, never actual buyer data.

## 7. 验收门槛 / Acceptance Gates

- ChatGPT 负责规划与代码修改，Codex 负责 Playwright 独立验收、问题反馈和提交中英双语测试文档；不得由 Codex 自行修改程序。
- ChatGPT owns design/source edits; Codex independently tests and may publish bilingual test documentation, but does not edit application code.
- UI V1 每批修改运行 Python、Node、Playwright 回归，必须与 S3/S4 现有安全约束兼容。
- Each UI batch reruns Python, Node and Playwright with existing S3/S4 safety invariants intact.
- 最终由用户在 Windows 实际操作：新建 → 导入物料与 PDF → 分配 → 报价 → 比价 → F5 读取 → 备份下载。
- Buyer manually tests Windows flow: create → items/PDF → allocate → quote → compare → refresh/reopen → backup download.
- 未通过人工验收之前，仅保留在 UI 独立分支；经明确批准后才提出合并到开发分支，`main` 保持不动。
- Keep UI V1 isolated until buyer approval to merge into the development branch; never touch `main`.

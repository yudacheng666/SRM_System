# 20261009 M1 数据模型与业务关系设计（草案）

> <sub>M1 Data Model and Business Relationships (Draft)</sub>

**目标：把已验收的 M0 交互变成有明确身份、历史保护、可保存和可恢复的数据结构。当前只设计，不开发。**
> <sub>Goal: formalize M0 into identity-safe, auditable and persistent data structures. This document is design only; no code is changed.</sub>

## 1. 模型边界与关键原则

1. 以 ERP 主数据字段名为准：`存货编码`、`存货名称`、`规格型号`、`所属类别`、`采购常用单位` 等；正式导入时保留原始 ERP 字段。
> <sub>1. Use ERP names for identical master-data fields and preserve raw source values.</sub>

2. 不创建脱离 ERP 的“统一物料编码”来取代存货编码。`RFQ Line ID` 仅是单条询价需求的稳定唯一身份；允许同一存货编码产生多个不合并的询价行。
> <sub>2. Do not invent a replacement inventory-code system. RFQ Line ID identifies the demand row; item codes may repeat across rows.</sub>

3. **已核实**：ERP `往来单位` 主表存在 `往来单位编码`、`往来单位名称`、`性质`、`供应商编码`。经用户确认，一家往来单位可兼具客户/供应商身份，且往来单位编码与供应商编码基本相同但**不强制相等**。供应商业务关联必须可追溯到同一个往来单位主体。
> <sub>3. The ERP counterparty template now confirms both the counterparty code and supplier-role code. One counterparty may hold customer and supplier roles simultaneously, and the two codes must not be forcibly equated.</sub>

4. 询价物料的字段来源应明确区分：ERP 主数据原值、采购员本次覆盖值、导入来源原文；主数据变化不能自动篡改已发 RFQ 快照。
> <sub>4. Separate master values, buyer RFQ overrides and raw import values; master updates must not rewrite issued RFQ snapshots.</sub>

5. 所有已确认报价、证据、人工定标理由和历史导入映射有不可覆盖的版本记录；不允许对历史做静默删除或原位覆盖。
> <sub>5. Confirmed quotes, evidence, buyer award reasons and import mappings are versioned and not silently overwritten/deleted.</sub>

6. M1 无供应商登录、无 ERP API 接口、无原始供应商数据上传 GitHub；采购员仍负责导入供应商回收报价。
> <sub>6. M1 does not require supplier logins, ERP APIs or real source data in GitHub; buyers import returned quotes.</sub>

## 2. 核心实体（按业务身份分离）

### E01 存货主数据 / ERP Material Master

身份：存货编码；来自 ERP Excel 导入；字段：存货名称、规格型号、所属类别、参考编码1、参考编码2、品牌、存货品牌、采购常用单位、计量单位、图号、版本号、材质、来源、关键等级等，字段是否存在以正式导出为准。
> <sub>ERP material master keyed by inventory code. Keep separate reference codes, unit fields and other verified master properties.</sub>

### E02 往来单位主数据及供应商身份 / Counterparty Master and Supplier Role

身份：ERP `往来单位编码` 为往来单位主体业务键，`往来单位名称` 是显示名称；客户、供应商是可以并存的业务身份。`供应商编码` 是供应商身份编码（与往来单位编码基本相同，但不假定永久相等），必须独立保留并建立明确映射。基础字段优先使用 `简称`、`性质`、`所属类别编码`、`所属类别`、`停用`；SRM 仅让供应商身份参与询价。姓名相似不是合并依据。
> <sub>Use one ERP counterparty record keyed by its counterparty code, with independently mapped supplier and customer roles. Supplier-role code stays a separate field; SRM RFQs only select records with a supplier role. Name similarity is not an identity key.</sub>

### E03 询价单 RFQ / RFQ Header

身份：RFQ 编号，可流水号、项目编号可为空；状态草稿/已发/完结；保存经办人、创建时间、来源及版本策略。
> <sub>RFQ header keyed by serial RFQ number, with optional project, lifecycle state and ownership metadata.</sub>

### E04 询价单版本 / RFQ Revision

身份：RFQ 编号 + 第 N 版；记录发布时点、变更说明、上一版引用及当期询价范围快照。任何已发 RFQ 实质变更必须新建版本。
> <sub>Issued RFQ revision snapshots are immutable; material changes create new revisions.</sub>

### E05 本次询价物料 / RFQ Line

身份：RFQ Line ID + RFQ 版本快照；字段至少有存货编码、存货名称、规格型号、询价数量、询价单位、图号/存货版本、采购员覆盖属性及原导入追溯。数量不同或技术条件不同的同码行不得无提示合并。
> <sub>Each RFQ demand line has stable line ID plus revision snapshot. Repeated item codes may remain separate for differing quantities/specifications.</sub>

### E06 供应商询价分配 / RFQ Assignment

关联：RFQ 版本 + RFQ Line ID + 供应商；多对多。每条记录有创建时间、分配来源、有效状态；Coverage 小于 100% 允许继续操作。
> <sub>Many-to-many line/supplier assignment with provenance and effective state; coverage below 100% remains allowed.</sub>

### E07 报价轮次 / Quote Round

身份：RFQ 版本 + 供应商 + 第 N 轮；记录该供应商本轮应报价 RFQ Line ID 集合快照，避免分配变更使历史漏报/多报误判。
> <sub>Supplier-specific quote round with an immutable expected line-scope snapshot.</sub>

### E08 轮内报价版本 / Quote Revision

身份：报价轮次 + 第 N 版；记录草稿、确认、作废（不物理删除）、确认时间及确认人员。新报价不能清空既有人工选择。
> <sub>Versioned supplier quotes within rounds; confirmed revisions retain history and do not erase buyer awards.</sub>

### E09 报价明细 / Quote Line

引用：Quote Revision + RFQ Line ID；有报价单价、报价币种、是否含税、报价计价单位、交期（天）及交期原文、MOQ、MPQ、报价状态、来源证据。不存在的供应商报价是漏报，不能用 0 占位。
> <sub>Quote line contains typed unit price, currency, tax, UOM, lead time, MOQ/MPQ and status; missing entries are omissions, never zero prices.</sub>

### E10 阶梯价格 / Price Tier

引用：Quote Line；档位数量起点、终点、适用单价、币种和单位。只在 RFQ 数量符合明确档位时参与比价；缺档位不猜测。
> <sub>Optional tier records with bounded quantities and unit prices; no inferred prices for unmatched quantities.</sub>

### E11 报价证据 / Quote Evidence

记录原始邮件及其附件，或聊天截图、独立 PDF 等原始来源的引用、文件摘要、收到时间、来源渠道、人工录入说明；保留与结构化报价的分离。
> <sub>Original emails/attachments or chats/PDFs provide evidence independently from structured quote data.</sub>

### E12 比价及采购员选择 / Award Decision

引用 RFQ Line ID、候选 Quote Line/Revision；记录默认最低价、人工选定供应商、非最低价原因、更新时间、复核状态；新一轮报价需保留旧决策并提示复核。
> <sub>Award decisions reference actual quote versions and preserve non-lowest rationale and review status.</sub>

### E13 历史采购订单事实 / PO Fact

引用原始订单编号、存货编码、供应商、订单状态、数量（主单位）、订单含税金额；“推算采购订单含税单价”只能作为独立的衍生值，不写入 Quote Line。
> <sub>PO facts are distinct from supplier RFQ quotes; a derived PO unit amount is not original quotation evidence.</sub>

### E14 历史询价资料 / Historical Import Batch

记录来源文件、源表/列/行、解析映射、证据等级、人工核查结果及异常；旧表“最终价格”先作为待核验谈判结果，不冒充已确认报价。
> <sub>Historical migration staging tracks row provenance and evidence quality; final negotiated amounts are not automatically confirmed quotes.</sub>

### E15 存货编码关联 / Code Reference

保留 ERP 存货编码与参考编码1/2、旧码、原厂号之间候选关联，含关联类型、来源、确认状态；1:1、1:N、N:1 或链式关系出现歧义时人工核查，不自动合并。
> <sub>Record old/new/reference code relations with source, match type and manual confirmation; ambiguous links never auto-merge.</sub>

### E16 变更日志与导入日志 / Audit and Import Log

记录导入批次、字段别名映射、原始行数、成功/失败/冲突数、操作者、时间、业务前后状态及关联对象版本，不把原始真实价格写入开发日志。
> <sub>Capture import and change provenance without leaking real quotes to developer logs.</sub>

## 3. 主要实体关系

存货主数据 `存货编码` → 多条 RFQ Line（1 对多）；每条 RFQ Line 属于一个 RFQ 版本快照，原始 `RFQ Line ID` 不随存货编码编辑而改变。
> <sub>One material code may occur in multiple RFQ lines; RFQ line identity remains stable across material-code edits and version snapshots.</sub>

RFQ Revision + RFQ Line ID ↔ 拥有供应商身份的**往来单位**，借助 RFQ Assignment 实现多对多；分配记录引用往来单位主体及供应商身份码，不能以显示名称作为关联键。
> <sub>RFQ assignments link line snapshots to supplier-role records tied to their canonical counterparty, rather than matching a supplier by display name.</sub>

供应商在每个 RFQ 版本下有多轮 Quote Round；每轮又有多个 Quote Revision；报价明细与阶梯价从属于确定的报价版本并引用当期 RFQ Line。
> <sub>A supplier may submit multiple quote rounds and revisions, each containing quote lines with optional tiers.</sub>

Quote Line ↔ Evidence 的来源关系可一对多：一封邮件附件可证明若干行报价，也允许单条报价来自截图或 PDF；没有证据的手工录入必须标识来源等级。
> <sub>Evidence and quote lines can have many-to-many provenance where one original attachment covers several lines.</sub>

Award Decision 关联到具体有效 Quote Revision/Line，不能只存供应商名称与数字金额。PO Fact 与 Historical Import Batch 单独保存，并可作为参考比较，不可倒灌成已确认供应商报价。
> <sub>Award decisions must point to specific quote revisions. PO history and import staging are reference facts, not substitute confirmed supplier quotations.</sub>

## 4. 严格状态与完整性校验

1. 报价状态：有效报价／明确未报价／不供货；`漏报` 是根据应报价范围与实际回收的差异计算出的缺失状态，`多报`、`重复`、`数据错误` 是校验结果。
> <sub>1. Quoted, explicit no-quote and cannot-supply are recorded states; omitted, extra, duplicate and invalid are derived validation states.</sub>

2. 价格和数量严禁空串强制变 0；真报零元价格与未报价是不同事实，需保留显式状态。
> <sub>2. Do not coerce missing values to zero; explicit zero-value quote differs from no quote.</sub>

3. 整批导入预览并检验唯一匹配；任何多候选关键字段、非法数量、报价版本历史冲突都必须显式告知并禁止静默写入。
> <sub>3. Preview batch imports and reject ambiguous keys, invalid quantities and history-conflicting changes.</sub>

4. 已确认报价、历史证据和版本不可原位更新。发布 RFQ 后修改数量、属性、供应商范围使用新 RFQ Revision；M1 不必一次完成完整 OA 审核流程。
> <sub>4. Confirmed quote/evidence/version records are immutable; changes after RFQ issuance create a new revision without requiring OA in M1.</sub>

5. 同范围比价：由采购员选择至少两家供应商；共同有效 RFQ 行使用相同询价数量，单价 × 数量得行金额；未报的不填零，保留计算来源。
> <sub>5. Buyer-selected groups of two or more suppliers compare identical valid RFQ lines at the same quantities without zero-imputing omissions.</sub>

## 5. M1 持久化建议与边界

M1 保留“离线 HTML 能直接打开”的目标，优先通过浏览器本地 IndexedDB 保存**结构化演示/采购工作数据**，并提供独立的“手动导出完整备份 JSON、导入前校验与恢复”功能；这是**建议设计，尚待你确认**。
> <sub>Proposed M1: browser-local IndexedDB persistence with explicit versioned JSON export/import and restore validation; this is a proposal pending confirmation.</sub>

浏览器本地数据不是云端同步：换电脑、换浏览器配置、清理网站数据或从不同 file:// 路径打开，都可能导致看不到原数据。必须提供操作明确的备份恢复和路径识别提醒，不能把本地存储说成 OneDrive。
> <sub>Browser-local storage does not provide cross-device synchronization, and local-file origins can behave differently. Require explicit backup/restore and warnings.</sub>

保存恢复时验证数据版本、RFQ Line ID 唯一性、报价引用完整性、历史不可覆盖及导入日志；恢复前允许预览，并确认覆盖或导入新的独立档案。
> <sub>Backups/restores must validate schema version, referential integrity and immutable quote history, with preview and explicit confirmation.</sub>

真实附件的长期存储方式（IndexedDB、浏览器目录或独立附件库）、自动备份路径、敏感数据加密以及未来服务器数据库/账号权限，M1 先设计接口、明确风险，不承诺仅靠 HTML 已能安全管理生产凭证。
> <sub>Attachment storage, automated backups, encryption and eventual server-side access control need separate design before production use.</sub>

所有正式采购和历史数据保存在用户指定的受控本地/公司云端位置，严禁提交 GitHub；GitHub 只维护代码、匿名测试和字段字典。
> <sub>Production data belongs in controlled company storage, never the source repository.</sub>

## 6. M1 与后续阶段的开发切分

M1：正式字段字典、统一导入模板、M0 交互字段改名兼容、结构化 RFQ/报价/供应商数据、基本保存及手动备份恢复；原始供应商文件仍可由采购员关联来源，不要求系统解析全部 PDF。
> <sub>M1 covers canonical schema, compatible imports, core entities, persistence and manual backup/restore, without universal PDF extraction.</sub>

M2/M3 候选：ERP 存货/供应商 Excel 主数据导入、参考编码关联和属性自动补齐、单位与税口径规则（按已核实数据推进）。
> <sub>Later stages can import ERP master data, code relationships, autofill and unit/tax normalization.</sub>

M4 及以后：真实 Excel/PDF 导出、图纸打包、历史报价证据归档、OA 报告、服务器部署与多用户权限；具体里程碑以再次确认的 PRD 为准。
> <sub>Real document packaging, evidence archival, OA reporting and multiuser server deployment remain later milestones.</sub>

## 7. 当前须确认的问题

**M1 本地持久化是否接受“IndexedDB + 手动备份恢复”作为过渡，而不是立即服务器数据库？** 若需要两台电脑共用同一份实时数据，应先讨论共享数据服务与访问权限。
> <sub>Confirm whether IndexedDB with manual backups is acceptable as the transitional storage; cross-device live collaboration requires a shared backend.</sub>

**ERP 存货档案与往来单位模板均已收到并核对所有表头**。仍待确认实际编码唯一性、主计量/采购常用单位换算、报价币种和税口径；在此之前不对真实采购数据做不可逆迁移。
> <sub>Both ERP master templates are now available. Actual identifier uniqueness, UOM conversion, currency and tax semantics still require validation before data migration.</sub>

## 8. 往来单位多身份和关联子表结构（已确认）

**关系一：往来单位主体（Counterparty）1 → N 身份（Role）。** 同一 `往来单位编码` 可在业务上同时为客户及供应商；只有具有供应商身份的主体才列入 SRM 本次询价供应商池。该模型不要求把客户和供应商物理拆成两个往来单位档案。
> <sub>A single counterparty can have both customer and supplier roles; SRM uses the supplier role without duplicating the master entity.</sub>

**关系二：往来单位主体 1 → N 联系方式。** 原 ERP Sheet `联系方式` 含 `所属往来单位编码`、`所属往来单位名称`、`编码`、`地址简称`、`联系人`、`电子邮件` 等 27 字段。以 `所属往来单位编码` 对应主档 `往来单位编码`；子表的 `编码` 是候选局部记录键，需后续验证唯一性。
> <sub>Contact/address rows refer to their parent through 所属往来单位编码. The child `编码` column is not assumed globally unique without examples.</sub>

**关系三：往来单位主体 1 → N 银行信息。** 原 ERP Sheet `银行信息` 含 `所属往来单位编码`、`所属往来单位名称`、`默认银行`、`账号`、`开户银行`。M1 保留结构但不导入/展示真实银行账户，也不将开户银行等信息复制到供应商基本表。
> <sub>Reserve a one-to-many bank-account relation and treat account details as sensitive. Do not ingest the banking child table into the initial SRM UI.</sub>

**关系四：往来单位主体 1 → N 数据协同设置。** 保留 `所属往来单位编码`、`协同对方系统`、`协同业务类型`、`对方往来单位对照编码` 等字段供未来接口使用；M1 暂不开发数据协同操作。
> <sub>Reserve counterparty-to-external-system mapping for future integration; no external synchronization is developed in M1.</sub>

**阶段范围：** M1 只需将 `往来单位` 主表的供应商基础属性纳入 SRM，三类子表保留实体关系、外键和必要的安全/唯一性约束设计，实际导入、编辑和多用户权限留待后续批准。`枚举档案` 属于模板辅助参考，不应当作主业务实体。
> <sub>M1 imports essential supplier attributes only. Model child-table relationships without activating full imports, editing or multiuser permissions. Enumeration reference sheets are not business entities.</sub>

> <sub>The field dictionary includes all 220 source columns with per-field implementation priority.</sub>

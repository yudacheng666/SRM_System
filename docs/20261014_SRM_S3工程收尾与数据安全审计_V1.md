- 在 GitHub Actions 查看 Windows CI，只有成功完成 Python 与 Node.js 测试才可标记自动化回归通过。
- Review Windows GitHub Actions; only a successful Python-plus-Node run establishes automated regression success.
- 故障演练使用独立的虚构询价和临时数据，不删除或篡改 `%LOCALAPPDATA%\SRM-Lite` 中用户现有测试资料。
- Simulate failures with disposable synthetic RFQs and temporary test data; never delete or corrupt the buyer's current test directory.

## 6. 下一阶段 S4 验收标准 / Next-Stage S4 Exit Criteria

- 先提供完整备份：SQLite 询价和历史快照、所有有关联的 PDF 原件，以及可校验文件索引；支持明确区分“内部完整备份”与“供应商外发包”。
- First provide a complete backup of SQLite, history, linked PDF bytes and verifiable index; separate internal recovery bundles from supplier-facing ZIPs.
- 恢复必须先预检查、再执行一致性恢复；任何缺文件、哈希不符、格式错误、重复工作区或版本冲突应明确拒绝，不能覆盖现有有效数据。
- Restore must preflight and apply atomically; missing files, failed hashes, bad archives, duplicates and revision conflicts must not overwrite valid data.
- 在一台全新、空白的测试数据目录内验证“备份 → 恢复 → 重开询价 → 重新打开 PDF → 比价结果一致”。
- Prove backup-to-restore in an empty test data root, including reopened RFQs, PDFs and equivalent comparisons.
- 完整恢复验收通过后，再设计自动保存、未保存变更提示以及备份保留策略。
- Only after recovery passes should autosave, unsaved-change warnings and retention policy be introduced.

## 7. 风险与当前使用限制 / Risks and Usage Limits

- 此版本仍是本地 SRM 开发原型；不要在其中录入唯一的一份真实采购数据。
- This remains a local SRM development prototype; do not use it as the sole home of real procurement records.
- 更新源码不会自动同步到正在运行的本地页面，需替换相应文件并刷新。
- GitHub source updates do not automatically replace the currently running local browser code; replace local files and refresh.
- 不合并 `main`，不删除本机原数据，不声称 CI 未核实的项目已经通过。
- Do not merge `main`, delete local records or claim unverified CI checks have passed.

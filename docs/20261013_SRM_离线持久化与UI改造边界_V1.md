# 20261013 SRM Offline Persistence and UI Scope V1

## 目标 / Goal

- 先在单台 Windows 电脑离线运行并完成业务原型及 UI 验收，之后交 IT 深化服务器部署。
- First complete an offline Windows buyer prototype and UI acceptance, then hand the system to IT for server implementation.
- 不在当前阶段开发 SSO、多用户权限、办公门户接入或企业级部署。
- No SSO, multi-user access control, intranet portal integration, or enterprise rollout in this phase.
- 不覆盖 `main`，不把真实公司、供应商、客户或产品数据写入仓库。
- Do not overwrite `main` or commit identifiable business, supplier, customer, or product data.

## 目标结构 / Target Structure

```text
Browser UI / 浏览器界面
      |
      | same-origin localhost HTTP API / 同源本机接口
      v
Local minimal service / 本机最小服务
      |
      +-- SQLite DB / 业务快照与历史版本
      +-- Assets / PDF、原始报价、邮件、截图
      +-- Verified backups / 数据库与附件完整备份
```

- 本机服务只监听 `127.0.0.1`，启动后由浏览器访问；不需要互联网。
- The local service binds to `127.0.0.1` only and serves a browser UI offline.
- 首版先以原 `M1WorkspaceCore` 快照格式为存储契约，避免在迁移开始时重做全部业务表。
- Start with the existing `M1WorkspaceCore` snapshot contract to avoid re-modeling every domain table during migration.
- 数据持久化层使用版本号条件写入；历史版本不能被静默覆盖。
- Use revision-based compare-and-swap persistence; never silently overwrite a committed revision.
- 下一阶段设计 `workspaces`、`workspace_versions`、`assets`、`asset_links`、`backup_manifests`。
- Plan `workspaces`, `workspace_versions`, `assets`, `asset_links`, and `backup_manifests`.
- 文件内容使用 SHA-256 校验，附件通过稳定标识关联到询价及物料；真实文件不进 GitHub。
- Validate file bytes with SHA-256 and reference them through stable IDs; do not commit real assets to GitHub.

## 数据保护要求 / Data Protection Requirements

- 每次成功持久化写入都需使用 SQLite 事务，且前端只有收到成功响应才能显示“已保存”。
- Every confirmed write must be transactional; UI may show “Saved” only after acknowledged success.
- 初期采用手动提交与防冲突策略，后续只对已确认的业务动作加入自动保存；不能靠每个任意点击触发保存。
- Begin with explicit commits and conflict detection; autosave later on confirmed domain changes, not generic clicks.
- 磁盘数据库与备份包不应保存在 Git 工作树内；避免把用户资料推送到 GitHub。
- Keep databases and backups out of the Git working tree to prevent accidental uploads.
- 备份必须同时覆盖数据库与全部附件原件，并附带校验清单；文件生成不等于恢复测试通过。
- Backups must include the DB, all originals, and checksums; creating an archive is not a restore test.
- 数据库备份不得对正在写入的 SQLite 文件直接进行普通复制；应使用 SQLite Backup API。
- Never plain-copy an active SQLite database; use the SQLite Backup API.
- 切换正式存储之前，先从现有版本导出完整 ZIP，并在独立环境验证恢复和关联数。
- Before switching storage, export the legacy complete ZIP and independently verify recovery and link counts.
- 服务器部署之后可替换数据库实现或增加鉴权；API 语义、ID、版本号和文件标识尽量稳定，但多用户并发仍需 IT 开发。
- IT may change the DB engine and add auth; API semantics, IDs, revisions, and asset identities should remain stable, while multi-user concurrency still requires development.

## UI 设计纪律 / UI Design Discipline

- 先做信息架构和页面线框图，再选择 Tabler 等组件库；组件库不决定业务流程。
- Define information architecture and wireframes before choosing Tabler or other component kits.
- 询价列表为入口，单笔询价页面包含物料与图纸、供应商分配、报价回收、比价议价。
- RFQ list is the entry point; each RFQ contains items/drawings, supplier assignment, intake and comparison.
- 数据管理、备份恢复和字段维护从日常询价流程中移出。
- Move data administration, backup/recovery, and field definitions out of day-to-day RFQ steps.
- 不因 UI 改版而删减多轮报价、阶梯价、双向分配、覆盖检查、图纸匹配及历史追溯。
- Do not remove rounds, tier prices, two-way assignment, coverage checks, drawing matching, or audit history.

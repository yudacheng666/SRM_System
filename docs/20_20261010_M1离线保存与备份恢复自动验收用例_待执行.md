## 二、测试数据及业务结构

> <sub>2. Synthetic fixture design</sub>

建立 100 条虚构存货、10 个往来单位、客户/供应商双身份、两种编码不相等的样例、1 张 RFQ、多版本/多轮报价、多供应商不重叠询价范围、阶梯价、明确未报价、不供货和非最低价选定理由；另设置没有邮件但有聊天截图/PDF **引用元数据**的报价。无需真实附件二进制内容。

> <sub>Fixtures contain 100 fake items, ten counterparties, dual roles, non-equal supplier codes, RFQ revisions, multiple quote rounds, tier prices, explicit omissions and manual non-lowest awards. Evidence references are synthetic metadata only.</sub>

特殊边界：零元有效报价与缺价不同；两家、三家供应商比较组的共同范围不同；同一存货编码允许多个 `RFQ Line ID`；重复旧码或参考编码须人工核查，不自动合并；`MOQ` 与 `MPQ` 不合并。

> <sub>Edge cases include genuine zero prices versus missing prices, changing common-scope groups, repeated inventory codes across RFQ lines, ambiguous aliases and independent MOQ/MPQ.</sub>

## 七、自动化测试实施说明（供后续开发者）

> <sub>7. Automation implementation guidance</sub>

建议用纯函数测试覆盖序列化、导入校验和恢复判断；Playwright 使用实际 `file://` 页面及浏览器文件选择/下载 API，保存不同工作空间的 snapshot 记录；故障注入必须确保只作用于虚构测试数据库。

> <sub>Use pure-function tests for validation/serialization and Playwright for actual file URL interactions. Inject failures only in synthetic isolated workspaces.</sub>

IndexedDB 在不同浏览器的 `file://` 作用域行为不保证一致，不能直接将一次云端浏览器运行结果推广到 Windows 公司电脑。持久化测试须显式使用持久化浏览器 profile 和固定路径，成功、降级、异常三种状态分别断言。

> <sub>Storage behavior under file origins differs across browser/platform. Test a persistent browser profile and fixed path, plus normal, degraded and failed states.</sub>

本文件只是验收设计，不应创建生产数据、发送邮件或自动定时备份，也不改变用户已批准的 M0 `main`。后续实现需先取得代码开发授权。

> <sub>This is a testing plan only. It does not create real records, send emails, schedule backups or modify main. Implementation requires separate approval.</sub>
